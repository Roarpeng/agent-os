# Architecture

## 流程

### 1. Goal / Constraints / I/O
- Goal：系统要达成什么，一句话 + 可量化验收标准。
- Constraints：区分硬约束（性能/成本/合规/已有技术栈）与软约束（偏好/时间）。
- I/O：输入（格式/频率/规模）、输出、错误交给谁。

### 2. Components
- 按职责划分组件，每个组件一句话职责。
- 数量最小化：先问"能不能合并"，再问"要不要拆"。
- 每个组件必须能回答：为什么它不是另一个组件的一部分？

### 3. Interfaces
- 组件间接口：数据结构、协议、错误语义。
- 接口先于实现定义；接口变更即架构变更。
- 接口带版本/演进策略，避免隐式耦合。

### 4. Data Flow
- 画主路径：数据从进入到输出的完整路径。
- 用图（Mermaid/SVG）表达组件与数据流，不用长文本。
- 标注同步/异步边界与数据一致性要求。

### 5. Failure Modes
- 每个关键组件回答三个问题：挂了什么样？怎么发现？怎么恢复？
- 关键失败路径必须有设计答案：降级 / 重试 / 告警。
- 跨组件故障：级联失败点要显式标出。

### 6. Verification
- 架构层面的验证手段：原型验证关键假设、压测瓶颈假设、故障注入验证恢复设计。
- 每个关键假设对应一个可执行的验证方法。

## 输出

1. 架构图（组件 + 数据流）
2. 组件职责表
3. 接口定义
4. 失效模式表（组件 × 症状 × 检测 × 恢复）
5. 开放问题与验证计划

## 原则

- 从约束推导设计，不从流行技术推导。
- 复用优先：先问现有代码/工具能否满足，再引入新依赖。
- 复杂度预算：宁可少一个组件，不多一层抽象。
- 给出取舍（trade-offs），不宣称唯一正确答案。
